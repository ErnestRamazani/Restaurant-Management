1. System context

Elite Restaurant supports in-house restaurant operations: floor tables, kitchen flow, cashier completion, money tracking, payroll-related utilities, reservations, and staff-facing tablet workflows. The same PostgreSQL database is accessed from:

  • The admin / back-office WPF application (rich UI, reporting, configuration).
  • The ASP.NET Core API (LAN tablets and the lightweight Server Portal UI).
  • Console utilities (seeding, maintenance).

Dependency rule: Core must not reference WPF or ASP.NET. The API and Pro both reference Core — this keeps domain rules portable.

3. EliteRestaurant.Core (domain kernel)

3.1 Responsibilities

  • Entity model — employees, products, tables, orders, reservations, money transactions, payroll artifacts, shared drafts, tablet sessions.
  • EF Core configuration — relationships, table names, value conversions (including timestamp handling documented in code comments).
  • Migrations — schema evolution under Migrations/.
  • Business utilities — e.g. OrderWorkflow, OrderTotalsHelper, OrderTotalsCalculator, PayrollCalculator, DataReconciler, FinancialTransactionService.
  • Cross-app services — SharedOrderDraftStore for persisted JSON drafts keyed by employee.

3.2 Design implications

Keeping “how we calculate totals” and “what counts as an active order” in Core means the WPF admin and API tablet path can align — when they do not, the bug is usually caller misuse or configuration precedence, not duplicated formulas.

4. PostgreSQL and EF Core

4.1 Why PostgreSQL

The system targets a networked database suitable for multiple clients (desktop + API) and concurrent access. Npgsql is the provider; connection strings are resolved via environment variables and/or persisted desktop settings.

4.2 Connection resolution

AppDbContext uses OnConfiguring when options are not pre-supplied (typical desktop/tooling path). The API registers a pre-configured pool using the same connection string helpers — ensuring one consistent source of truth for credentials.

4.3 Pooling on the API

Program.cs configures AddDbContextPool<AppDbContext>(..., poolSize: 32) with retry-on-failure for transient network errors. This is the recommended posture for ASP.NET Core apps hitting remote PostgreSQL.

4.4 Migrations and startup

DatabaseInitializer.Initialize() is invoked at API startup (and similar patterns exist on desktop) so schema is brought current. Operators should treat migration failures as blocking deployment events.

4.5 Reconciliation

DataReconciler.ReconcileTableStatusesWithOrders enforces consistency between Orders (active statuses) and Tables.Status, skipping maintenance tables. This is idempotent repair logic — important after partial failures or manual DB edits.

5. EliteRestaurantPro (WPF desktop)

5.1 Technology

  • .NET 8, WPF, net8.0-windows
  • MVVM — ViewModels inherit base types (e.g. AdminBaseViewModel), views in Views/
  • Styling — shared resources (e.g. Resources/Styles.xaml), per-view XAML
  • Reporting — QuestPDF and related exports

5.2 Database bootstrap UX

First-run and retry paths use a WPF dialog (DatabasePipeSetupDialog) for pipe-separated PostgreSQL fields instead of legacy VB-style input boxes — improving validation, accessibility, and visual consistency.

5.3 Create-order refactor (application architecture)

The create-order screen is a high-complexity feature (open checks, discounts, reservations, tablet flows). The codebase now separates:

  • TableLoadingService — EF queries for tables, menu, reservations, delivery references.
  • DraftPersistenceService — JSON payload shape + SharedOrderDraftStore integration.
  • OrderSubmissionService — transactional create/append paths, inventory hooks, reconciliation calls.
  • OrderTotalsCalculator (Core) — wraps discount parsing, OrderTotalsHelper, and prep estimation.

The ViewModel (CreateOrderViewModel, ~1,000+ lines) remains large because it still owns observable state, command wiring, and user messaging — acceptable if business rules stay out of it.

6. EliteRestaurant.Api (HTTP + hosting)

6.1 Role

The API is a LAN-first service: expose JSON endpoints for tablets, serve static portal files, optional HTTPS via PFX.

6.2 Key components

  • Controllers — ServerPortalController, TablesController, ReservationsController, HealthController, AuthController
  • Security — TabletAuthService (scoped) validates bearer tokens against TabletSession
  • DTOs — dedicated request/response records under Dtos/
  • Swagger — developer ergonomics; consider gating in production

6.3 CORS

CORS policy requires configured origins — the API fails fast if none are listed. This matches a known set of tablet browser origins rather than open wildcard.

6.4 Static files

UseDefaultFiles + UseStaticFiles serves wwwroot/index.html as the Server Portal shell.

7. Server Portal: HTML, CSS, and static delivery

7.1 Implementation style

The portal is a single-page style document: wwwroot/index.html embeds a large <style> block (dark theme, grid layout, responsive breakpoints) and inline behavior in <script>. This trades long-term modularity for deployment simplicity (no npm build pipeline on the server).

7.2 CSS architecture (observed)

  • CSS variables for color-scheme: dark and typography
  • Layout via display: grid (.layout, .two-cols)
  • Component-like classes: .card, .nav-btn, .list-box, .muted
  • Responsive: sidebar collapses under ~1000px width

7.3 Maintainability notes

For senior review: the portal is straightforward to read but will benefit from extracting CSS/JS into separate files if multiple engineers edit it concurrently. A bundler is optional; even static file split improves diff clarity.

8. Authentication and sessions

Tablet login flows create TabletSession rows with tokens and expiry. Validation is per-request via TabletAuthService.Validate. The API controllers check the session before returning sensitive operational data.

Desktop uses separate concepts (AppSession, admin/staff login flows) appropriate to a thick client.

9. Configuration: appsettings, env, IOptions

Dual sources exist by design:

  • Desktop / Core file settings via SettingsManager (business profile, currency pricing, rounding)
  • API appsettings for infrastructure: CORS origins, LAN HTTPS ports, certificate paths, and CurrencyPricing section bound to IOptions<CurrencyPricingOptions>

Senior maintainers should document precedence: e.g. API tax/service rates may override file defaults when explicitly positive — verify in ServerPortalController and keep parity tests.

10. Refactor narrative: create-order and shared logic

10.1 Motivation

Large ViewModels complicate testing and encourage duplicated submission logic between surfaces. The refactor moves deterministic and transactional work into services while preserving WPF bindings in the ViewModel.

10.2 Cross-cutting Core helpers

  • OrderDiscountParser, OrderPrepTimeEstimator
  • OrderSubmissionHelper (assignee resolution, payment field sync, reservation link)
  • OrderTotalsHelper / OrderTotalsCalculator

10.3 Pattern to replicate

  1. Identify a ViewModel region with DB access + domain rules.
  2. Extract pure logic to Core when it has no UI dependencies.
  3. Extract orchestration to a Pro sealed class service when it needs AppSession or WPF-specific messaging boundaries.
  4. Leave the ViewModel as state + ICommand + dialog coordination.

11. Test architecture

EliteRestaurant.Tests targets net8.0 and references Core only (not WPF), enabling fast CI. InMemory EF tests validate reconciliation behavior without PostgreSQL.

Gap: API integration tests (WebApplicationFactory) are not described in this repository snapshot — adding them would validate auth + controller contracts.

12. Operational tools and data lifecycle

12.1 SeedRunner

Destructive reseed: truncates and rebuilds sample data. Guarded by interactive confirmation (restaurant name) with --force for automation. Runbook should state: backups, correct connection string, and least-privilege roles for non-prod.

12.2 ClearActiveOrders

Maintenance utility for operational cleanup — treat like any production-affecting binary.

14. WPF UI architecture (patterns)

14.1 MVVM boundaries

Views (*.xaml) declare layout and bindings; ViewModels expose observable properties and ICommand instances. Navigation is typically mediated by a root shell (MainWindow) and/or delegate callbacks passed into ViewModels (e.g. Action<BaseViewModel> navigate pattern).

14.2 Resource dictionaries

Shared brushes, control styles, and typography should remain in Resources/Styles.xaml (and merged dictionaries) so individual feature views stay focused on layout. Senior reviewers should watch for inline styles duplicated across views — a maintenance tax.

14.3 Dialogs vs. main window

Modal flows (database setup, confirmations) use dedicated Window subclasses. This is preferable to OS-specific input boxes for validation, accessibility, and branding consistency.

15. Transactions and consistency

Several write paths wrap Database.BeginTransaction() around SaveChanges() plus follow-up reconciliation (e.g. order append/create in OrderSubmissionService and API server portal). The architectural intent is:

  • Atomic inventory + order lines where both must succeed or neither.
  • Post-commit reconciliation to repair derived state (table occupancy).

Senior reviewers should verify that new write paths either participate in an explicit transaction or document why read-committed single calls are sufficient.

16. Deployment checklist (LAN / single-site)

  1. PostgreSQL — version compatibility with Npgsql/EF; backups enabled (PITR or nightly dump).
  2. Migrations — run via app startup or controlled pipeline; verify migration history on prod clones.
  3. API — configure Cors:AllowedOrigins; place PFX for LAN HTTPS if used; document passwords in secret store.
  4. Desktop clients — distribute connection settings via GPO or installer; DPAPI secrets are per-user/per-machine.
  5. Operational tools — restrict who can run SeedRunner; never store prod connection strings in shared scripts.
