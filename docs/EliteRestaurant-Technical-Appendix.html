C. Startup Sequence Detail

C1. Desktop startup

Order Action Why it matters
1 Enable legacy Npgsql timestamp behavior. Compatibility layer during date/time migration from older storage assumptions.
2 Register unhandled exception hooks. Writes crash information to local logs and keeps operators informed.
3 Configure QuestPDF community license. Enables PDF/report functionality.
4 Check for --import-sqlite-now. Provides migration path from local legacy DB to PostgreSQL.
5 Ensure PostgreSQL connection string exists or prompt user. Application is PostgreSQL-required in active mode.
6 Attempt database initialization in a retry loop. Allows operator to correct a bad connection string at startup.
7 Apply theme palette and continue to UI shell. Final presentation setup before view rendering.

C2. API startup

Order Action Effect
1 Enable legacy timestamp behavior. Keeps DB date compatibility aligned with desktop startup.
2 Call AppDbContext.Initialize(). API startup can create or patch schema before serving requests.
3 Add controllers, Swagger, auth service, CORS. Configures REST surface and API discoverability.
4 Enable Swagger, CORS, default files, static files, controllers. Serves both API and portal from the same host.

E. Indexes and Relationship Notes

  • Unique indexes exist for employee unique ids, product unique ids, table unique ids, and order unique ids.
  • Employee.SignInId is unique when populated and non-empty.
  • Table.TableNumber is unique.
  • ReservationBooking.ReservedFor and status are indexed for time and state filtering.
  • SharedOrderDraft is indexed by employee, portal, and update time for recent draft retrieval.
  • Attendance uniqueness is enforced on employee plus work date.
  • Payroll uniqueness is enforced on employee plus year plus month.

F1. Authentication

Method and route Input Success behavior Failure behavior
POST /api/auth/login staffId, pin, optional portal Returns access token, expiration, employee identity, role, and sign-in id. Unauthorized if id, pin, and portal role do not resolve to a valid active employee.

F2. Server portal configuration and media

Method and route Purpose Notes
GET /api/server/config Return restaurant name, logo URL, employee photo URL, currency mode, exchange rate, tax and service settings. Requires a valid server session.
GET /api/server/assets/restaurant-logo?token=... Serve the restaurant logo file from local path stored in settings. Uses token in query string rather than bearer header.
GET /api/server/assets/me-photo?token=... Serve the logged-in employee photo file. Reads file path from employee record in database.

F3. Server operational data

Method and route Purpose Key validation
GET /api/server/products Return menu items ordered by category, subcategory, and name. Server session required.
GET /api/tables/my Return non-maintenance tables, filtered to assigned tables for server role. Any valid session can call; server session narrows results.
GET /api/server/open-check?tableId=... Determine whether the table has an open active order. Table must exist and be assigned to current server.

F4. Shared drafts

Method and route Purpose Behavioral notes
GET /api/server/drafts Return up to 50 recent drafts for the server employee. Ordered by latest update first.
POST /api/server/drafts Save a new JSON snapshot draft. Request body must contain valid JSON in SnapshotJson.
DELETE /api/server/drafts/{draftId} Delete a draft owned by the current employee. Draft id must belong to the logged-in employee and server portal.

F5. Orders and ready queue

Method and route Purpose Important validation and side effects
POST /api/server/orders Create a new order or append to an open check. Checks table assignment, maintenance status, valid products, discount rules, delivery reference, and recalculates table occupancy and payment totals.
GET /api/server/ready-orders Return ready orders for the current server. Includes line summary and totals in both USD and FC.
POST /api/server/orders/{orderId}/serve Mark a ready order as served. Only the owning server can call it, and only from the Ready state.

F6. Reservations and health

Method and route Purpose Notes
GET /api/reservations/arrived List recently arrived reservations. Returns up to 100 rows with table label information.
GET /api/health Process heartbeat endpoint. No DB check beyond service liveness.
GET /api/health/db Quick DB connectivity check with employee and table counts. Returns HTTP 500 with exception message on failure.

G. Browser Portal Internal Logic

The browser portal is intentionally minimal and stores runtime state in JavaScript variables instead of browser persistence. The token is kept in a variable rather than localStorage or sessionStorage. As a result, a refresh or tab close will remove the active session from the UI side even if the API token still exists server-side.

Concern Observed implementation
State storage In-memory variables: token, current user, tables, products, ready orders, drafts, config, and cart.
HTTP wrapper Single api() helper that adds bearer header when needed and parses JSON opportunistically.
Filtering Client-side search plus category and subcategory filtering over preloaded product list.
Totals Client-side subtotal, discount, tax, service, and grand total calculation for immediate feedback.
Draft snapshots Serializes current form state and cart to JSON, then restores from snapshot on load.
Order submission Builds API payload directly from DOM state and cart contents.

I. Workflow Deep Dive

I1. Server order creation flow

  1. Server logs in with staff id plus PIN using portal type Server.
  2. Portal loads branding config, assigned tables, products, ready orders, and drafts.
  3. Server selects a table, order source, payment currency, discount, and products.
  4. Portal optionally checks whether an open check already exists on the table.
  5. API validates server ownership of the table and product existence.
  6. API either appends to the open check or creates a new OrderRecord.
  7. Payment totals are recalculated server-side using shared helpers.
  8. Table status is reconciled and remains occupied while the check is open.

I2. Draft round-trip flow

  1. The portal captures order form state and the cart as a JSON snapshot.
  2. A server draft is saved with a generated human-readable label.
  3. The database stores the snapshot as PayloadJson in SharedOrderDrafts.
  4. Loading a draft restores the table, notes, currency, discount, append mode, and cart.
  5. The UI explicitly resets search and category filters so the full menu remains visible after load.

I3. Payroll computation flow

  1. Determine scheduled workdays and hours for the month from the employee shift pattern.
  2. Count absences and late days from attendance rows.
  3. Convert every four late days into one deduction unit.
  4. Compute base salary after attendance deductions.
  5. Compute a five percent bonus on the employee's generated sales where relevant.
  6. Subtract applicable salary advances.
  7. Write a payroll payment snapshot and, when positive, a salary expense transaction.

I4. Financial posting flow

Completed orders can create revenue entries in Transactions. The code uses a structured justification string to avoid duplicate revenue postings. A helper also aligns revenue transaction dates with order completion timestamps when necessary. This indicates that financial records are expected to reflect the business date of actual order completion rather than simple creation time.

K. Technical Observations and Risks

K1. PostgreSQL-first with SQLite residue

The active runtime clearly expects PostgreSQL, but the codebase still contains significant SQLite-era material: import routines, disabled schema methods under conditional compilation, and at least one utility that appears to expect a DatabasePath. This is not inherently wrong, but it means new contributors should not assume the code has been fully normalized after migration.

K2. Schema evolution without migrations

Startup-driven schema mutation is workable for small teams, but it has tradeoffs. There is no migration history, rollback strategy, or environment-to-environment migration discipline represented in the repo. For local development and direct operator-managed installations, this may be acceptable. For larger deployments or strict change management, it is a notable limitation.

K3. Web portal maintainability

The portal is efficient in deployment terms but expensive in long-term maintainability. Styling, UI structure, client state, and API calls are all in one file. Changes are easy to ship quickly, but the file will become progressively harder to test and reason about as portal scope grows.

K4. Auth simplicity

The auth model is perfectly understandable but intentionally lightweight. It is suitable for a trusted local environment, especially when the host machine is physically controlled. However, it is not yet a hardened API authentication design. If future scope includes internet exposure, cross-site access, or multiple organizations, auth should be reconsidered early rather than late.

K5. Mixed UI and shared-core responsibility

EliteRestaurantPro is both an application and a reusable domain source. That is convenient today, but it means a web-facing API depends on a project that also contains WPF-specific concerns. A future restructuring into separate class libraries for domain, data access, and desktop UI would reduce coupling.
